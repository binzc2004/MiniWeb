### MiniWeb 框架库模拟发布与集成验收

**为什么要做：**

此前 MiniWeb 一直作为一个独立的 Maven 项目进行开发，通过 `mvn install` 虽然已经能够将项目打包并安装到本地 Maven 仓库，但这并不能完全证明它已经具备作为独立框架库供其他项目使用的能力。因此，需要模拟真实的第三方开发者使用场景，将 MiniWeb 作为一个 Maven 依赖引入全新的 Java 项目，验证框架的依赖管理、API 暴露、自动装配和运行流程是否完整。通过这一过程，可以发现框架内部实现与外部使用接口之间的问题，确保使用者无需了解 MiniWeb 的内部实现，只需引入依赖、编写配置类和 Controller，就能够启动自己的 Web 服务。

**完整实施过程：**

1. **整理框架项目：** 检查 MiniWeb 项目结构，确保框架源码位于 `src/main/java`，测试代码位于 `src/test/java`，删除不必要的示例代码和临时文件，完善 `pom.xml` 中的 `groupId`、`artifactId`、`version`、依赖声明及构建配置。
2. **构建并安装框架：** 在 MiniWeb 项目根目录执行 `mvn clean install`，完成编译、测试、打包，并将生成的 JAR 安装到本地 Maven 仓库。
3. **创建独立使用项目：** 在 MiniWeb 项目之外新建一个 Maven 项目，将其视为第三方开发者的应用项目，不直接依赖 MiniWeb 源码，也不复制框架内部代码。
4. **引入 Maven 依赖：** 在新项目的 `pom.xml` 中添加 MiniWeb 依赖，通过 `groupId`、`artifactId` 和 `version` 从本地 Maven 仓库解析框架。
5. **验证框架使用接口：** 在新项目中编写带有 `@MiniWebApplication` 注解的启动类，通过 `MiniWeb.run()` 启动框架；创建带有 `@RestController`、`@GetMapping` 和 `@PostMapping` 注解的 Controller，实现简单的 HTTP 接口。
6. **验证核心功能：** 启动应用，通过浏览器或 curl 测试 HTTP 请求，检查路由匹配、路径参数、请求参数绑定、JSON 请求与响应、404 和 405 错误处理、静态资源访问以及并发请求处理。
7. **检查外部依赖与运行环境：** 验证新项目能够正确解析 MiniWeb 的传递依赖，检查日志输出、Jackson 序列化和反序列化等功能，确保框架不依赖原项目的运行目录或开发环境。
8. **完成集成验收：** 确认第三方项目仅通过 Maven 依赖即可使用 MiniWeb，且不需要修改框架源码。最后整理使用示例、项目 README 和依赖配置，形成一个可以供其他开发者参考的框架使用案例。

**验收标准：**

- [ ] MiniWeb 能够通过 `mvn clean install` 成功安装到本地 Maven 仓库。
- [ ] 独立 Maven 项目能够正常解析 MiniWeb 依赖。
- [ ] 第三方项目能够通过 `@MiniWebApplication` 启动服务。
- [ ] 能够通过 Controller 注解注册和访问 HTTP 接口。
- [ ] HTTP 请求、参数绑定、JSON、异常响应和静态资源功能正常。
- [ ] 第三方项目不需要访问或修改 MiniWeb 的内部源码。
- [ ] 框架能够在独立项目中正常运行，完成从开发项目到可复用 Maven 框架库的转换。

**最终目标：** 模拟真实框架使用者的开发体验，验证 MiniWeb 已经从一个独立的 Java Web 服务器实现，转变为一个能够通过 Maven 依赖集成、通过注解配置、通过统一入口启动的轻量级 Web 框架。
