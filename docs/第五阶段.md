## 第五阶段
### 需求描述
第五阶段主要是对前四个阶段实现的 MiniWeb 进行工程化整合，使其从一个能够处理 HTTP 请求的基础原型，逐步成为一个可以稳定运行的轻量级 Web 框架。首先引入线程池，将客户端连接处理任务交给线程池执行，实现多客户端并发访问；然后增加静态资源处理能力，支持 HTML、CSS、JavaScript 和图片等文件访问；接着统一各层异常处理和日志记录，确保单个请求发生异常不会影响服务器运行；同时完善 Socket 超时、资源释放和服务器优雅关闭机制，避免连接长期占用资源或服务器被强制终止；最后整理 Maven 依赖、项目结构和启动入口，完成整体功能验收。本阶段重点不在于增加复杂框架特性，而在于提高现有功能的稳定性和完整性，并继续采用构造器注入、明确组件职责等设计，为下一阶段实现 IoC 容器做好准备。
下面是验收清单：
[ ] 使用线程池处理客户端连接。
[ ] 支持多个客户端同时发送 HTTP 请求。
[ ] 支持 HTML、CSS、JavaScript、图片等静态资源访问。
[ ] 统一处理参数错误、路由错误和服务器内部异常。
[ ] 单个请求异常不会导致服务器退出。
[ ] 使用 SLF4J + Logback 统一管理日志。
[ ] 设置 Socket 读取超时。
[ ] 确保 Socket、输入输出流等资源正确释放。
[ ] 实现服务器优雅关闭。
[ ] 整理 Maven 依赖和项目结构。
[ ] 完成完整示例项目，能够正常启动和运行。

### 开始开发
#### 1.引入线程池
为什么做： 目前服务器采用什么方式处理客户端连接，决定了它能否同时服务多个客户端。如果每接受一个连接就创建一个新线程，连接数量增加后会产生较大的线程开销。我们需要用线程池统一管理工作线程。

具体怎么做：
1. 创建线程池，使用 ExecutorService 管理工作线程。
2. 修改 MiniWebServer：每次 accept() 接收到客户端连接后，不再直接创建线程，而是将连接处理任务提交给线程池。
3. 保留现有的 ClientHandler，继续负责单个 Socket 的处理和关闭。
4. 处理线程池拒绝任务的情况，避免连接资源泄漏。
5. 暂时不实现优雅关闭，先验证并发功能，关闭机制留到后续阶段完善。

#### 2.实现静态资源的访问
一、为什么做？
目前 MiniWeb 主要通过 Controller 返回字符串或 JSON 数据，但一个完整的 Web 框架还应该能够提供网页文件。例如 HTML 页面需要加载 CSS、JavaScript 和图片。本阶段让 MiniWeb 不仅能处理动态接口，也能直接提供静态网页资源。
二、怎么做？
我们新增一个静态资源处理模块，建议放在 com.miniweb.staticresource 包下：
1. StaticResourceHandler：负责根据 HTTP 请求路径查找资源文件，读取文件内容并构造 HttpResponse。
2. MimeTypeResolver：根据文件扩展名确定 Content-Type，例如 HTML、CSS、JS、PNG、JPEG。
3. 静态资源目录：在项目中建立 static 目录，存放 HTML、CSS、JS 和图片。
4. 请求分发整合：在现有请求分发流程中增加静态资源处理入口，区分静态资源请求和 Controller 接口请求。

#### 日志管理
MiniWeb 已经使用 SLF4J 作为日志门面，因此没有必要再造一套日志接口。我们希望框架内部和框架使用者都通过统一入口获取日志对象，同时将日志实现的选择权留给使用者。具体做法是在 MiniWeb 门面类中增加静态方法 getLogger(Class<?> clazz)，内部调用 LoggerFactory.getLogger(clazz) 并返回 SLF4J 的 Logger；框架内部继续直接使用 SLF4J，用户则可以自行引入 Logback 或 Log4j2 等日志实现，并通过对应配置文件控制日志级别、格式和输出位置。这样既统一了使用入口，也避免了框架与具体日志实现耦合。

#### 超时与资源释放
目前 MiniWeb 已经使用线程池处理并发连接，但客户端可能建立连接后一直不发送数据，或者发送一半请求后停止，导致工作线程长期阻塞、占用 Socket 和线程池资源。因此需要增加超时控制和资源释放机制。我们主要通过 Socket.setSoTimeout() 设置读取超时时间，限制客户端读取请求时的等待时间；同时确保 Socket、输入输出流和线程池任务在异常、超时及正常结束时都能正确释放。这里不需要实现复杂的连接管理器，优先利用 Java Socket 自带的超时机制。

#### 框架组建
目前用户必须在 main() 中手动创建每个组件、处理它们之间的依赖关系；而框架的价值之一，就是把这些重复的组装工作隐藏起来。我们让 @MiniWebApplication 保存应用配置，让 MiniWeb.run(Application.class) 读取配置、确定扫描包，再按正确的依赖顺序创建组件并启动服务器。这里借鉴 Spring Boot 的启动方式，但暂时不引入 YAML 和 IoC 容器，Controller 仍然由现有的 ControllerRegistry 通过无参构造器创建。
